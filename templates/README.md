# Bot templates

Copy `c_bot/` or `cpp_bot/`, rename it, and write your strategy in
`choose_action()`. Both templates already handle the parts that are easy to get
wrong: ABI checking, raise clamping including the short all-in case, and the
safe fallback action.

## Build

From inside a copied template directory:

```sh
make FELT_INCLUDE=/path/to/felt/harness/include
```

or with CMake:

```sh
cmake -B build -DFELT_INCLUDE=/path/to/felt/harness/include
cmake --build build
```

or directly:

```sh
clang -O2 -std=c11 -fPIC -fvisibility=hidden \
  -I/path/to/felt/harness/include \
  -dynamiclib -o my_bot.dylib my_bot.c
```

Use `clang++ -std=c++17` and `my_bot.cpp` for the C++ template. The only build
input Felt needs is `harness/include/felt/bot_api.h`; there is nothing to link
against.

## Run

```sh
run_match my_bot.dylib /path/to/felt/build/debug/bots/check_call.dylib \
  --hands 2000 --seed 1 --out ./results/smoke
```

Start small and seeded. `check_fold`, `check_call`, `always_all_in` and
`seeded_random` make useful first opponents — `always_all_in` in particular will
find raise-sizing bugs immediately.

To add a bot to Felt's own build instead, drop it under `bots/` and add one line
to `bots/CMakeLists.txt`:

```cmake
add_felt_bot(my_bot my_bot/my_bot.c)
```

## The rules that bite

**`amount_to` is a total, not an increment.** `RAISE_TO.amount_to` is your
total contribution *on the current street*, not the chips you are adding. To
raise to 600 when you have already put in 100, send 600, not 500. This is the
single most common bot bug.

**All-in is not a separate action.** Use `RAISE_TO{max_raise_to}`, or `CALL`
when the call already takes your stack.

**Short all-ins invert the raise bounds.** When the only raise available is an
all-in smaller than a full raise, `max_raise_to < min_raise_to`, and the one
legal amount is exactly `max_raise_to`. Clamping to `min_raise_to` first
produces an illegal action. Both templates check this in the right order.

**Trust the legal-action mask.** Do not infer legality from `to_call` or the
street. The mask is generated by the same code that validates your reply.

**Illegal actions are not clamped.** An illegal action or amount becomes check
if legal, otherwise fold, and a violation is logged. Felt deliberately does not
fix your bet size, because that would hide the bug.

**Randomness must come from `decision_random`.** No `rand()`, no clocks, no
global counters. Seed a small PRNG from it, as both templates do. The same state
must always produce the same action.

**Be a pure function.** No state carried between hands or matches, no threads,
and never retain a pointer from the state — `state->history` is valid only for
the duration of the call.

**C++ must not leak exceptions.** An exception crossing the `extern "C"`
boundary is undefined behaviour and takes the match worker down with it. The C++
template wraps the strategy in a catch-all.

**Names must outlive the call.** `felt_bot_name()` returns a pointer good for
the life of the process: a string literal or a static buffer, 1 to 127 bytes.

## Timing

Each decision has a CPU cap (default 2 ms, `--decision-cap-ms`). It is measured
on your thread's own CPU clock *after* the call returns, so machine load is not
charged to you. Exceeding it does not forfeit — your action is replaced by check
or fold and a violation is logged, which costs you chips.

Separately, a wall-clock hard timeout (default 1000 ms, `--hard-timeout-ms`)
ends the whole match with exit code 124 if a decision never returns. That one is
terminal, so an infinite loop aborts the match rather than losing one hand.

Expensive immutable tables should be built once, not per decision: a
function-local static in C++, or a lazily-filled file-scope table in C. Nothing
prevents you doing that work inside the first timed decision, so warm it in
`felt_bot_name()` if you would rather not pay the cap there.
