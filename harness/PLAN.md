# Harness implementation plan

This is the implementation sequence for [SPEC.md](../SPEC.md) and
[GAME_RULES.md](../GAME_RULES.md). Version 1 targets trusted C bots on macOS and
uses direct in-process calls. Isolation and hostile-submission security are not
part of this plan.

The order is intentionally short: freeze the small public API, prove the poker
engine, then add reporting and performance work.

## M0 — Build and public API

1. Create a CMake C++17 project targeting 64-bit macOS 12 or newer.
2. Add Debug, Release, and ASan/UBSan presets plus a test framework.
3. Define the C-compatible public types and three exported bot functions.
4. Pin ABI version, struct sizes, field meanings, and legal-action bits.
5. Build always-fold, check-call, always-aggressive, and seeded-random reference
   bots as dynamic libraries.

Done when the harness loads two libraries, validates their ABI versions and
names, calls each directly, and rejects malformed libraries with clear setup
errors.

## M1 — Cards, random streams, and evaluator

1. Implement the card encoding in GAME_RULES.md.
2. Implement SHA-256 domain derivation, xoshiro256++, unbiased bounded sampling,
   and the pinned Fisher-Yates shuffle.
3. Add golden tests for seed derivation, PRNG output, full deck order, and
   duplicate-pair identity.
4. Vendor OMPEval after confirming its license and card convention.
5. Wrap it behind evaluate7() and cross-check at least 10 million random
   seven-card hands against a simple reference evaluator.

Do not use std::shuffle or standard-library distributions in any
reproducibility-sensitive path.

## M2 — Betting engine

Implement one hand without dynamic bots first. Tests precede the match runner.

Required scripted cases:

- button folds preflop;
- button limps and the BB receives its check/raise option;
- check-through on every postflop street;
- opening bet, raise, re-raise, and all-in;
- short all-in that does not reopen action;
- attempted raise after action was not reopened;
- fold to a bet on every street;
- river showdown and a chopped pot;
- effective-stack enforcement and zero-sum chip reconciliation.

The public legal-action mask and every sizing field must be generated by the
same legality code used to validate returned actions.

## M3 — Dealer and duplicate match runner

1. Implement the exact positional deal order from GAME_RULES.md.
2. Play adjacent duplicate hands with the same positional cards and swapped bots.
3. Reject an odd --hands value when duplication is enabled.
4. Alternate the button and generate a fresh deal per hand without duplication.
5. Reset equal stacks every hand and accumulate net chips by bot and position.
6. Validate all CLI chip values and require 0 < small blind < big blind <= stack.

Done when scripted matches reconcile to zero chips globally and both hands of
every duplicate pair share their cards exactly.

Use always-aggressive versus always-fold for a simple betting oracle.
Always-fold versus check-call is not an oracle because one orientation can check
through to showdown.

## M4 — Logging and replay

1. Write versioned summary.json and one complete JSONL record per hand.
2. Record bot hashes, configuration, cards, normalized actions, state-facing
   sizing fields, violations, timings, and raw/adjusted results.
3. Flush in bounded batches so a crash loses little output without forcing a
   system call for every line.
4. Replay logged cards and actions through the engine and require an identical
   terminal state.
5. Add a separate seed-and-bot rerun diagnostic.

Timing values are part of the historical log and are not reproducible. There is
no byte-identical-output requirement.

## M5 — Exact all-in equity

1. Enumerate remaining boards on flop and turn.
2. Enumerate and memoize exact preflop matchups.
3. Canonicalize swapped matchup keys and reverse the result on lookup.
4. Store integer wins and ties; use a wide intermediate for pot multiplication.
5. Apply the BB remainder rule and retain the seeded raw runout.
6. Test known matchup ranges and duplicate-swapped cache hits.

There are 812,175 unordered disjoint exact-combo matchups. Start with a
match-local lazy cache. Persistent caching or a generated complete table should
be added only if profiling shows preflop all-ins are a practical bottleneck.

## M6 — Statistics

Implement the definitions in SPEC.md exactly:

- headline adjusted net chips and bb/100;
- raw wins, losses, and chops;
- bucket and exact-combo rows split by position;
- VPIP, PFR, c-bet, WTSD, and W$SD;
- action counts and fractions by street;
- CPU/wall timing and violation distributions.

Cross-footing tests must prove that combo totals equal bucket totals, position
totals equal headline totals, and raw wins plus losses plus chops equal hands
played.

## M7 — Timing, performance, and release

1. Measure each direct call with macOS CLOCK_THREAD_CPUTIME_ID and
   CLOCK_MONOTONIC.
2. Replace actions that return over the configured CPU cap and log the violation.
3. Document that bots are single-threaded and that v1 cannot recover from hangs
   or crashes.
4. Benchmark full 40,000-hand matches on a named reference Mac.
5. Record evaluator throughput, decisions per hand, JSONL size, and duplicate
   pair-level variance.
6. Run tests under ASan/UBSan and perform long-match soak testing.
7. Write the bot-author guide from the final public header and ship a minimal C
   bot template.

The 7–15 minute target and the default 2 ms cap are provisional until measured
on the reference machine.

## Deferred work

- A separate worker-process mode with recoverable CPU/wall timeouts.
- Filesystem, network, process, and syscall restrictions for untrusted bots.
- Enforced per-hand address-space reset.
- Other bot languages through a process protocol.
- Persistent equity tables, AIVAT, and the separate rating tool.
